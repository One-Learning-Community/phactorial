# API audit before 1.0

Status: ruled on 2026-11-18. The maintainer accepted every recommendation in the decisions below, including the `xarrow()` reorder: few callers exist yet, so the risk is small. Two notes from the ruling are written into decision 4 and the sequence. The symbol rulings stand as proposed and are the work list for 0.19.

Scope: every public symbol in `phactorial/phactorial` (core) and `phactorial/commonmark` at `d2ded4b`, found by reflection over `src/`. Each symbol gets a proposed ruling and a one-line reason. Quoin, the one downstream consumer, is checked out at `122a9f70` (its 0.18.0 release); every symbol it reads is marked with the files that read it. An independent review checked the symbol list, the Quoin marks and the rulings against the code; its corrections are folded in.

## How to read the tables

Rulings:

- **public**: frozen at 1.0 as it is.
- **public, renamed**: frozen at 1.0 under the new name given. The old name goes in 0.19, with no alias.
- **public, changed**: frozen at 1.0 after the change described.
- **internal**: stays in the code with `@internal`. No promise, and no support for calling it.
- **remove**: deleted in 0.19.

"Already" means the code marks it `@internal` today. Quoin paths are relative to Quoin's `packages/`; "tests" means Quoin's test suites only. Constructors and static factories that only the library calls are ruled internal even on public classes, so fields can be added later without breaking callers.

Three facts frame every ruling.

PHP's named arguments make parameter names part of the API. `Math::layout(font: $f)` breaks if `$font` is renamed. Every parameter name and default on a public method freezes with the method, so the renames below include parameters.

A return type freezes too. `Math::frac()` returns `Fraction`; widening it to `Node` after 1.0 breaks callers who rely on the narrower type.

Every class is `final` except two open types. `Node\Node` is abstract, so a user can subclass it; the writers then throw on the unknown subclass, except `TexWriter`, which writes nothing. `Layout\DisplayItem` is an interface, so a user can implement it; the library's own tests do (`tests/Layout/CountedItem.php`). Adding a method to either after 1.0 breaks every implementer. Decisions 1 and 2 seal both.

## Decisions

Most consequential first.

### 1. The node tree

**Recommendation: users may walk the tree, through `children()` and public read-only properties, and build it only through `Math`. `Node` is sealed. Builders never wrap and keep their narrow return types. Adding a node type is a minor release; code that switches on node types must carry a default.**

The tree is the hub: readers produce it, `MathRender::node()` hands it out, and the writers consume it. A user who wants to lint a formula, count its fractions or write a format the library lacks must walk it. Every public property on the node classes is already `readonly`, so walking by property works today.

Make `children()` public as well. Typed properties serve a walker that knows every type. A walker meeting a type added in a later minor, or a wrapper such as `TexSource`, has only `children()` to recurse through; without it the walker skips the whole subtree and says nothing. Promise every child in reading order, and nothing about the count.

Building by hand is different. A constructor is where an invariant lives: `Grid` derives `$columns` and pads alignments, `Identifier` derives `$upright`, `Space` clamps. `Math` validates and tokenizes. Freezing constructors freezes those signatures and lets callers build trees the engine never makes, which the writers must then accept forever. Build through `Math`; keep constructors internal.

Builder return types. Most builders return a concrete class (`frac(): Fraction`, `sup(): Scripts`, `binom(): Fenced`); `row()` and a few others return `Node`. Narrow types are useful, and builders validate by throwing, so they never need a wrapper. Keep them, and promise that a builder returns exactly the class it declares.

Freeze:

- the set of classes, by name and namespace;
- `children()`: every child, in reading order;
- every public property: its name, its type and its meaning;
- builder return types;
- the shape the readers produce for a documented construct (`\frac` reads as a `Fraction`), at the level of class and property.

Do not freeze:

- which wrapper nodes the readers place between those shapes (`TexSource`, `DisplayStyle`, `Fallback`);
- the nesting of `Row` inside `Row`.

New node types. PHP has no sealed classes. Say in the docs that `Node` must not be extended. PHPStan's `@phpstan-sealed` on `Node`, listing the subclasses, enforces that for PHPStan users; before adopting it, check whether PHPStan then treats a `match` over the list as exhaustive, which would endorse the missing default the policy forbids. The BC policy says a minor may add a node type, every `match` or `instanceof` chain over nodes needs a default, and the library's writers handle every type it ships. A walker that meets an unknown node recurses through `children()` and can fall back to `TextWriter::write()` for it.

The alternative is an opaque tree: promise only `Math`, `MathRender` and the writers. It is safer and contradicts the hub direction, since a writer outside the library would have nothing to read. Recommend against.

### 2. The layout output

**Recommendation: make `Box`, `DisplayItem`, `Glyph` and `Rule` public and freeze them for reading. Keep their constructors internal. Seal `DisplayItem`. Fix the set of item kinds at `Glyph` and `Rule` for all of 1.x; a new kind reaches a backend only when the backend asks for it.**

The docs already promise this. The backend guide calls it "a public display list" and walks through `each()`, `Glyph`, `Rule`, `$box->items` and `glyphPaths()`. Pulling it back would break a documented feature.

What Quoin reads:

- `Box` as a type, `$width`, `$ascent`, `$descent`, `each()`, and a bare `new Box($width, 0.0, $height)` built only to size `glyphPaths()`;
- `Glyph::$gid`, `$text`, `$x`, `$y`, `$size`, `$sx`, `$sy` and `translated()`, which is `@internal` today;
- `Rule::$x`, `$y`, `$w`, `$h`;
- `SvgRenderer::glyphPaths()` and `Font::gid()`.

That is the documented surface plus `translated()` and the `Box` constructor. Promote `translated()`; it is pure. Replace the constructor call by changing `glyphPaths()` to take a width, ascent and descent. The engine's constructor then stays internal, with its engine-only parameters.

The silent-drop risk. Quoin's `MathPainter` skips any item that is neither `Glyph` nor `Rule`, and so does the guide's own example. A third kind would vanish from PDFs without an error. Pinning Quoin to `~1.x.0` only delays that, and forces a Quoin release on every Phactorial minor, today's `^0.18` problem kept for life.

Close the set instead. In 1.x, `each()` and `$items` yield only `Glyph` and `Rule`; say so in the docs and the BC policy. If a later feature needs a new kind (a diagonal stroke for `\cancel`, say), it ships behind an opt-in: a new optional parameter on `Math::layout()` naming the extra kinds the caller can draw. Without it, layout draws the feature from glyphs and rules or leaves it out with a note, as the readers do today. Adding an optional parameter is a minor, and a backend written against 1.0 never sees an item it cannot draw.

A `fallback()` method on `DisplayItem` was considered and rejected. It would have to exist in 1.0 to be any use, since an old backend never calls a method added later, and some future kinds have no faithful drawing in glyphs and rules.

Quoin's painter should still throw on an unknown item in its tests, so a contract slip fails CI before it reaches a PDF.

### 3. Output stability

**Recommendation: adopt the proposal, with the boundary drawn by what a program can observe.**

Breaking after 1.0:

- `MathRender::svg()`: the root element's `role`, `aria-label`, `aria-hidden` and inline `vertical-align` style and their meaning; `width`, `height` and `viewBox`; CSS pixels as the unit; `currentColor` as the default color, wherever in the markup the fill sits.
- `SvgRenderer::render()`: `width`, `height`, `viewBox`, the units, and the default color `#000000`. It writes no ARIA attributes.
- `SvgRenderer::glyphPaths()`: a view box of `0 -ascent width height`, which puts the baseline at y = 0, and `overflow="visible"`. Quoin's workaround depends on both.
- The display list's conventions: points; y down; the origin at the left end of the baseline; a `Glyph`'s `x` and `y` at its origin on the baseline; `sx` and `sy` scaling about that origin; a `Rule`'s `x` and `y` at its top-left corner.
- MathML: the namespace, the `display` attribute, the element chosen for a construct (`\frac` is `<mfrac>`), and the attributes that carry meaning (`mathvariant`, `stretchy`, `accent`).
- OMML: element choice per construct, the run properties `RunFormat` sets, and alignment values.
- TeX and text writers: that output read back yields an equivalent tree, and that `text()` stays a plain, speakable string.
- PNG: transparent background, the pixel-size formula in the docs, and `MathPng`'s fields.
- Notes: their `element` values, and which level a construct gets, within the limits decision 4 sets.

Not breaking:

- spacing, kerning, glyph choice, stretch and `big()` sizes, rule thickness, and every coordinate in the display list, SVG paths and PNG pixels;
- SVG structure below the root (`<g>`, `<path>`, transforms) and the number of paths;
- the `aria-label` text, which comes from `text()` and improves with it;
- redundant MathML wrappers such as an `<mrow>` around one child;
- note `reason` text.

The SVG emits no class names today. Keep it that way: a class becomes an API the day someone styles it.

Defaults. Two layers have two sets of defaults, and output.md presents the split as deliberate. `MathRender` serves web pages: inline, 16 pixels, `currentColor`. The lower layers serve their formats: `Math::layout()` and `MathmlWriter::write()` default to display style, `Math::layout()` to 12 points, and the renderers to black. Freeze that rule in writing and apply it everywhere; `oMathPara()` is the one member that breaks it today.

Goldens may change in any minor. The changelog lists every golden change under its own heading.

### 4. TeX and MathML coverage

**Recommendation: coverage grows in minors; the handling of unsupported input is frozen.**

Today an unknown TeX command is drawn as its name and carries a `Dropped` note (`\nosuch{x}+1` gives `Dropped \nosuch unknown command`). An unknown MathML element is drawn as its contents with an `Approximated` note. The commonmark extension keys on `Dropped` to show the source instead.

Frozen:

- readers never throw, on any input;
- every unsupported construct produces a note, with the level set by one rule: `Dropped` when content is lost, `Approximated` when it is drawn differently;
- the documented input limits, and what each does when hit. Most truncate and note. At `MAX_DEPTH` the deeper TeX groups are drawn as their source; deep MathML is flattened to text.

Not breaking:

- supporting a command that was unknown. Output changes for documents that used it, and its note disappears. List each in the changelog.
- a note moving from `Dropped` to `Approximated` as support improves.

Breaking:

- dropping support for a command, or changing what a supported command means;
- a supported construct newly producing a `Dropped` note.

A user who needs byte-stable output pins a patch range. The policy says so once.

Ruling: no removal of a supported command is foreseen. Every command in the reader is there for a reason. The policy states the rule anyway, and if a command must ever go, it is deprecated first: it keeps working with an `Approximated` note naming the replacement, and it leaves only in a major.

### 5. The CommonMark contract

**Recommendation: the config keys, the HTML shape, the fence and paragraph behavior, the node properties and the three priorities are contract. The classes behind them are internal.**

- Config keys and values: contract. New keys and values may arrive in minors.
- HTML shape and classes: `span.math.math-inline`, `span.math.math-display`, `div.math.math-display`, and the error forms `code.math.math-error` and `div.math.math-display.math-error > code`. Users target them in CSS and the docs print them. Inside the wrapper sits `<svg>` or `<math>` by `output`, governed by decision 3.
- Fences: a fence whose first info word is `math` is typeset; every other fence falls through to the next renderer.
- The listener's effects: a paragraph that is only `$$…$$` becomes a display block, and math inside link text or image alt text goes back to its source text, as on GitHub.
- Priorities: the inline parser registers at 50, the `FencedCode` renderer at 50, and the `MathInline` and `MathBlock` renderers at the default 0. The Laravel mail recipe overrides them by registering at 10 and 100, and the fence fix depends on outranking highlighters at 10. Changing a number silently breaks those overrides. Document all three.
- Node properties: `MathInline::$tex`, `$display` and `$source`, and `MathBlock::$tex` and `$source`. The mail recipe reads the `$tex` and `$display` fields.

Config, priorities and HTML shape are not visible to reflection, so each gets its own test.
